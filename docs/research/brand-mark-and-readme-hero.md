# Research: What design directions exist for a Mosaix brand mark and README hero, beyond the three already prototyped (A/B/C)?

> **TL;DR**: Five structurally distinct directions hold up against the primary sources: **D — Compass** (directional-focus ticks on a single cell, banner radiates outward from one focused cell); **E — Monogram** (the wordmark's own "M" carries the tiling motif, no separate pictorial icon); **F — Live screenshot** (an almost-bare split-square icon paired with a real annotated screenshot hero, the pattern [komorebi](https://github.com/LGUG2Z/komorebi/blob/master/README.md) and [Rectangle](https://github.com/rxhanson/Rectangle/blob/main/README.md) actually ship); **G — Depth stack** (z-order/focus cards instead of spatial partition, but conflicts with Microsoft's own perspective guidance and is the weakest at 16px); and **H — Terminal bracket** (a two-stroke `[ ]` glyph plus a literal CLI-chrome banner, cheapest to draw and safest at small sizes). Every illustrated banner examined from a real, comparable project — [GlazeWM](https://github.com/glzr-io/glazewm/blob/main/resources/assets/logo.svg), [Hyprland](https://github.com/hyprwm/Hyprland/blob/main/assets/header.svg), and [yabai](https://github.com/koekeishiya/yabai/blob/master/assets/banner/banner.svg) — converts its lettering to `<path>` outlines with zero live `<text>`/`font-family` use, which lines up with the SVG Working Group's requirement that an SVG referenced as an image runs in "secure static mode" with external references disabled ([SVG Integration §3.6](https://svgwg.org/specs/integration/)). Separately, GitHub's own sanitizer allowlist (`html-pipeline`'s `SanitizationFilter`) does **not** include the `svg` element, so a hero authored as inline `<svg>` markup pasted into a README is stripped; it must be shipped as a referenced image file (`<img>` or `<picture><source>`), which GitHub then serves through its Camo proxy. yabai's banner shows a genuinely different, cheaper alternative to GitHub's documented `<picture>`/`prefers-color-scheme` two-file pattern: a **single** self-theming SVG with an internal `<style>` block containing its own `@media (prefers-color-scheme: dark)` rule, referenced by one plain `<img>` tag.

## Findings

### What's already on the table, and what any new direction must fit

Three directions exist in [`apps/mosaix-settings/src/prototype-branding.ts`](../../apps/mosaix-settings/src/prototype-branding.ts) and must not be re-proposed: **A "Quadrant"** (a 2×2 grid of rounded squares, left-weighted banner with a separate tiled-monitor inset), **B "Split"** (a recursive binary-split icon; the banner *is* a tiled layout with the wordmark occupying the focused cell), and **C "Snap frame"** (stroke corner-brackets plus a solid block snapped into a corner and a dashed ghost block; a centred typographic title-page banner). All three already support both palettes defined in [`apps/mosaix-settings/src/styles.css`](../../apps/mosaix-settings/src/styles.css): `.night-tide` (`--ground:#080a0d`, `--ink:#f1f4f5`, `--accent:#ff7558`, `--zone-line:#78dcd5`) and `.warm-paper` (`--ground:#e9e3d8`, `--ink:#282721`, `--accent:#c94f2e`, `--zone-line:#b54d30`). The incumbent icon, [`apps/mosaix-settings/src-tauri/app-icon.svg`](../../apps/mosaix-settings/src-tauri/app-icon.svg), is a fixed-palette 512×512 rounded-square (rx 112) containing four 142px rounded squares (rx 24) rotated 4°.

The domain glossary in [`CONTEXT.md`](../../CONTEXT.md) supplies vocabulary A/B/C leave untouched: **Zone**, **Zone cycle**, **Balanced grid**, **Grid reflow**, **Active tiling set**, **Session-floating window**, **Focus border**, **Snap preview overlay**, **Visual window order**, **Directional focus**, **Directional swap**, and **Display migration**. A/B/C encode spatial partition (grid, split, frame) exclusively; none touch focus, movement, floating, or z-order.

### Platform icon guidance (what "survives at small sizes" actually means)

Microsoft's Windows app-icon design guidance, fetched directly, sets the concrete legibility bar: icons align to a **48×48 grid**, with a **2px exterior-corner radius / 1px interior-corner radius at 48×48**, and the explicit instruction to "use as few shapes with as few corners as possible to distinguish your product while still feeling at home on Windows" ([Design guidelines for Windows app icons](https://learn.microsoft.com/en-us/windows/apps/design/iconography/app-icon-design)). The same page states plainly: **"Icons should not include typography as part of the design. Letters and words on your icon should be avoided and only used when it's essential."** It also licenses a *progressively simplified* icon at small sizes (its own worked example is a record player that sheds detail as it shrinks) and warns against perspective/isometric treatment for anything but the simplest metaphors: "The icon on the right is too complex for perspective, so using it for this icon is not recommended."

Microsoft's companion asset-construction page gives the actual pixel grid Windows renders at — **16, 20, 24, 30, 32, 36, 40, 48, 60, 64, 72, 80, 96, 256** px via `targetsize-*` — and states the bare minimum an app must ship is **16×16, 24×24, 32×32, 48×48, and 256×256** ([Construct your Windows App's Icon](https://learn.microsoft.com/en-us/windows/apps/design/iconography/app-icon-construction)). It also documents the exact MSIX manifest sizes already present in `apps/mosaix-settings/src-tauri/icons/` — `Square44x44Logo` (44px base), `Square150x150Logo` (150px base), `Square71x71Logo` (71px), `Square310x310Logo`, `StoreLogo` (50px base) — and states that a plated/backgrounded icon requires **separate light- and dark-theme asset variants** to be re-implemented by hand ("Icons look best with a transparent background... you'll have to re-implement some theming functionality that transparent icons get for free... you might provide a version of your app's icon plated on two different backgrounds, one better suited to a light theme and the other to a dark theme.").

I could not verify Apple's Human Interface Guidelines "App icons" page directly: `developer.apple.com/design/human-interface-guidelines/app-icons` renders through client-side JavaScript, and direct fetches returned only the page's `<title>` with no body content. I'm not asserting the commonly-repeated canvas/corner-radius numbers for it here, since I could not confirm them against Apple's own text — this is a real gap in the sourcing for this document, not a settled fact.

### The Tauri icon pipeline as a hard, already-committed constraint

`apps/mosaix-settings/src-tauri/tauri.conf.json`'s `bundle.icon` array lists exactly `icons/32x32.png`, `icons/128x128.png`, `icons/128x128@2x.png`, `icons/icon.icns`, `icons/icon.ico` — and Tauri's own docs confirm this is the standard `tauri icon` output: the command takes **one** squared PNG or SVG source with transparency and produces that five-file set, plus a `Square*Logo.png`/`StoreLogo.png` MSIX set that Tauri's docs describe as **"currently unused but intended for AppX/MS Store targets"** ([App Icons | Tauri](https://v2.tauri.app/develop/icons/)) — which matches the `Square30x30Logo.png` … `Square310x310Logo.png`/`StoreLogo.png` files already sitting in `src-tauri/icons/`. Two consequences for any new direction: (1) the pipeline bakes from a **single fixed-palette source**, so it cannot itself produce Microsoft's recommended separate light/dark-plate variants — those would have to be hand-authored and wired in outside `tauri icon` if wanted; (2) regenerating the whole icon pyramid for a new mark is one command (`tauri icon <source>`), so the *icon* side of any direction below is cheap to ship regardless of which one is picked — the cost differences below are almost entirely in the *banner*.

### README hero mechanics on GitHub (verified constraints, not opinion)

**Inline `<svg>` markup does not survive.** GitHub's markdown pipeline sanitizes rendered HTML — `github/markup`'s own README states the resulting HTML is "sanitized, aggressively removing things that could harm you and your kin" ([github/markup](https://github.com/github/markup)) — and the actual allowlist used downstream, `html_pipeline/sanitization_filter.rb`'s `ALLOWLIST`, lists `img`, `picture`, and `source` as permitted elements but **does not include `svg`** ([`sanitization_filter.rb`](https://github.com/gjtorikian/html-pipeline/blob/main/lib/html_pipeline/sanitization_filter.rb)). Practically: a hero authored as literal `<svg>…</svg>` pasted into `README.md` gets its `<svg>` tag stripped on render. It must be shipped as a **file**, referenced via `<img src="...">` or `<picture><source>`.

**`<picture>` + `prefers-color-scheme` is the documented, current mechanism for theme-switching a README image.** GitHub's own developer blog documents exactly this pattern — `<picture><source media="(prefers-color-scheme: dark)" srcset="dark.png"><source media="(prefers-color-scheme: light)" srcset="light.png"><img src="default.png"></picture>` — for "repo README files, documentation hosted on GitHub, and any other Markdown files rendered on GitHub.com" ([How to make your images in Markdown on GitHub adjust for dark mode and light mode](https://github.blog/developer-skills/github/how-to-make-your-images-in-markdown-on-github-adjust-for-dark-mode-and-light-mode/)), and GitHub's `about-readmes` page confirms `<picture>` is a supported element. A `github/community` discussion with a GitHub staff reply confirms this superseded an older, undocumented `#gh-dark-mode-only`/`#gh-light-mode-only` URL-fragment convention: "using the HTML `<picture>` construct is the best option from multiple points of view... We came up with a solution that makes it work with the GitHub theming system" ([community discussion #16910](https://github.com/orgs/community/discussions/16910)).

**A referenced SVG is proxied, not embedded live.** GitHub rewrites `img`/image `src` attributes in rendered markdown to route through its Camo image proxy, which — per Camo's own documentation — "restricts proxied images content-types to a whitelist" and rejects non-`image/*` responses (`atmos/camo`, the reference implementation GitHub's proxy descends from: [atmos/camo](https://github.com/atmos/camo)). This means a referenced `.svg` file is served *as an image resource*, not parsed into the page's live DOM.

**That "as an image" distinction is exactly what breaks external fonts.** The SVG Working Group's Integration spec defines two processing modes for exactly this situation — an SVG document referenced by an HTML `img` element (or a CSS `<image>` value) must run in **secure animated mode** or **secure static mode**, both of which explicitly set "external references" to **disabled**, alongside disabled scripting and (in static mode) disabled declarative animation ([SVG Integration §3.4 / §3.6](https://svgwg.org/specs/integration/)); SVG2's own `<image>` element section makes the same requirement ("SVG files must be processed in secure animated mode if the current document supports animation, or in secure static mode if the current document is static," [SVG2 §12.3](https://www.w3.org/TR/SVG2/embedded.html)). A `@font-face` pointing at an external font file is an external reference, so a README-hero SVG cannot reliably pull in Inter or Segoe UI Variable this way — and empirically, **every illustrated banner examined from a comparable, real project converts its lettering to `<path>` outlines and uses zero live `<text>`/`font-family`**: GlazeWM's `resources/assets/logo.svg` (viewBox `0 0 542 94`, confirmed no `<text>` tag and no `font-family` property anywhere in the file — [file](https://github.com/glzr-io/glazewm/blob/main/resources/assets/logo.svg)), Hyprland's `assets/header.svg` (all letterforms as `<path>`/`<polygon>`, gradient fills only, no `@font-face` — [file](https://github.com/hyprwm/Hyprland/blob/main/assets/header.svg)), and yabai's `assets/banner/banner.svg` (same — [file](https://github.com/koekeishiya/yabai/blob/master/assets/banner/banner.svg)). This is a unanimous, three-for-three empirical pattern among the illustrated banners this research could read, not a single example.

**A single self-theming SVG is a real, cheaper alternative to the two-file `<picture>` pattern.** yabai's `assets/banner/banner.svg` is referenced by one plain `<img width="75%" src="assets/banner/banner.svg" alt="Banner">` in its README ([`README.md`](https://github.com/koekeishiya/yabai/blob/master/README.md)) — a single file — yet the SVG itself contains a `<style>` block with `.text {...}` rules overridden inside an internal `@media (prefers-color-scheme: dark)` rule that recolors the text fill for dark viewers. This works because Camo's documented content-type whitelist behavior still serves the file as `image/svg+xml`, and because an embedded `<style>` block (unlike an external stylesheet reference) is not the kind of "external reference" the SVG Integration spec's secure modes disable — the CSS lives inside the same file. I did not independently capture live response headers from `camo.githubusercontent.com` to confirm this beyond Camo's documented whitelist behavior, so treat that last mechanical detail as inferred from the documented sources rather than independently re-verified here.

**Truncation and content width.** GitHub's `about-readmes` page states any README content beyond **500 KiB is truncated** when viewed on GitHub. I could not find an officially documented maximum content/image width for rendered READMEs in GitHub's own documentation — this should be treated as unverified rather than asserted at a specific pixel figure; a relative-width (`width="100%"` or a `viewBox`-only SVG) sidesteps the question rather than relying on an unconfirmed number.

### Five directions beyond A/B/C

#### D — Compass (directional focus)

**The idea in one line:** the mark is a single rounded cell with short accent-colored ticks touching only the edges that have a live neighbor, encoding **Directional focus**/**Directional swap** rather than static partition geometry; the banner puts one large focused cell at centre with the wordmark inside it, and thin leader lines/ticks point outward to small labelled feature cells — motion radiating from one cell, not a grid filled edge-to-edge like A or B.

**Evidence:** no project examined here (A/B/C included) visually encodes movement/interaction rather than partition shape, so this is not directly precedented among the comparable-project logos read — flagged honestly rather than claimed. What supports its *feasibility* is Microsoft's shape guidance, which explicitly rewards "as few shapes with as few corners as possible" ([app-icon-design](https://learn.microsoft.com/en-us/windows/apps/design/iconography/app-icon-design)) — a single cell with a few ticks is close to that ideal — and the domain grounding is `CONTEXT.md`'s own **Directional focus** and **Directional swap** entries, which have no visual representative in A/B/C today.

**Small-size survival:** workable but untested at the extreme. At 32px, a rounded square with 2–4 short ticks reads as distinct from A's checkerboard and C's brackets. At 16px, short ticks at typical stroke widths risk fusing into the cell's silhouette and reading as texture noise rather than direction — Microsoft's own "progressive abstraction" precedent licenses shipping a simplified 16px-only variant that drops the ticks entirely, falling back to a plain rounded square, but that's an extra asset to draw and maintain that A/B/C don't need.

**Palette fit:** trivial — one accent-colored cell (`--accent` #ff7558 night-tide / #c94f2e warm-paper) with ticks in `--zone-line` (#78dcd5 / #b54d30). No new tokens needed.

**Production cost:** icon is cheap (single `tauri icon` source, few paths). Banner needs the satellite-cell layout work (comparable to B's cell-count complexity) plus the same font-portability handling as every other direction — path-convert or embed the wordmark for the README asset per the SVG-secure-mode finding above.

#### E — Monogram (letterform-as-tile)

**The idea in one line:** there is no separate pictorial icon — the wordmark's own "M" is cut into two or three tiled, individually-tinted panes along its strokes, so the app icon *is* the monogram and the banner is one continuous wordmark with only that "M" carrying the tiling treatment; no inset preview, no grid, no cell layout.

**Evidence:** GlazeWM's real, shipped identity fuses a colored mark directly against the wordmark in one drawn asset rather than treating them as separately composable pieces ([`logo.svg`](https://github.com/glzr-io/glazewm/blob/main/resources/assets/logo.svg)), which is adjacent to this idea but not the same — GlazeWM's mark and lettering are still visually separate shapes side by side, not one letterform carrying the tiling motif internally. I did not find a project among the seven read here that cuts a letterform itself into tiled panes; this is a novel combination for this space, not a directly precedented one.

**Small-size survival:** this is the one direction that runs directly against a specific, quoted platform rule for the *icon* half: Microsoft's guidance states plainly, **"Icons should not include typography as part of the design... only used when it's essential"** ([app-icon-design](https://learn.microsoft.com/en-us/windows/apps/design/iconography/app-icon-design)). A single reduced monogram glyph is a lighter violation than a full wordmark-as-icon, and at 32px a two- or three-pane "M" can likely stay legible, but at 16px the internal tile seams will almost certainly disappear, leaving a plain solid "M" — an acceptable full-abstraction fallback, but the direction spends its entire concept on the one visual device platform guidance most directly warns against.

**Palette fit:** single accent color per theme, trivial.

**Production cost:** highest icon-design cost of the five — the letterform can't be a system font run through `tauri icon`; it has to be hand-drawn/cut into paths from the start (unlike A/B/C's simple rectangles). The banner needs the same treatment throughout, so there's no "live text now, convert later" shortcut the way there is for D, G, or H.

#### F — Live screenshot (screenshot-first)

**The idea in one line:** the icon deliberately stays close to a plain color swatch — a single rounded square split by one thin off-center line, encoding just one **Zone** boundary rather than a full grid — and the banner drops illustration entirely, becoming a real annotated screenshot of the `mosaix-settings` spatial editor with zone/feature callouts, the way komorebi and Rectangle actually do it.

**Evidence:** komorebi's README goes straight from its `# komorebi` heading to a real screenshot with no logo at all ([`README.md`](https://github.com/LGUG2Z/komorebi/blob/master/README.md)), and Rectangle's top-of-README image is a real 962×886 application screenshot, not a designed banner ([`README.md`](https://github.com/rxhanson/Rectangle/blob/main/README.md)) — both are actively maintained, directly comparable window-management tools that reject illustrated heroes in favor of literal product truth, which directly contradicts the shared assumption behind A/B/C that the hero must be an illustrated SVG.

**Small-size survival:** the best of the five for the icon specifically, because it carries almost no detail — a single split square is close to the minimum shape count Microsoft's guidance rewards, and simpler than any of A/B/C. The banner isn't subject to icon-size constraints at all.

**Palette fit:** the icon reskins trivially with `--accent`/`--zone-line` per theme. The banner is the hardest of the five to theme-match losslessly: it's a **raster capture** of one specific palette at one moment, so a true light/dark pair needs two real screenshots (or two renders of the prototype UI), swapped via GitHub's documented `<picture>` + `prefers-color-scheme` mechanism — which, unlike every other direction here, has no font-portability problem at all, since there's no live SVG text to break.

**Production cost:** the icon is the cheapest to draw of the five. The banner's cost is dominated by product readiness rather than illustration skill: it needs a screen worth screenshotting and annotating, and `README.md`'s own **Status** section currently reads "Early development -- workspace scaffolded, implementation not yet started." The `prototype-branding.ts`/spatial-editor UI already in the repo is the only candidate surface today, so this direction is honestly premature until there's a real screen to show.

#### G — Depth stack (focus/z-order)

**The idea in one line:** the mark encodes z-order and **Focus border** instead of spatial partition — two or three rounded cards offset diagonally, the front one outlined in accent color (focused), the back ones desaturated or dashed (echoing **Session-floating window**); the banner is the same stack peeled apart like a hand of cards, wordmark on the front focused card, feature callouts on the cards behind it.

**Evidence:** none of A/B/C touch z-order or focus state — they're exclusively spatial-partition metaphors. Microsoft's own icon-layering guidance directly supports a card-stack mark as an on-platform pattern: "Icons are composed of flat objects sitting on top of the layers below it... Use drop shadows within icons to create definition between object layers" ([app-icon-design](https://learn.microsoft.com/en-us/windows/apps/design/iconography/app-icon-design)) — but the same page's Perspective section is a direct, quoted caution against exactly the diagonal/offset treatment this idea wants: "The icon on the right is too complex for perspective, so using it for this icon is not recommended" for metaphors with multiple layered objects, meaning any offset has to stay very shallow and flat, not isometric.

**Small-size survival:** the weakest of the five. Two or three overlapping rounded rectangles with individually distinguishable strokes/opacity is more shape-count than Microsoft's "use as few shapes with as few corners as possible" ideal supports; at 16px the offset cards are likely to fuse into a single blob unless the offset is large relative to card size, at which point the "stack" reading breaks anyway. This direction most plausibly needs a dedicated, simplified 16px glyph (collapse to just the front card) — which Microsoft's own progressive-abstraction example licenses, but which is a maintenance burden none of A/B/C/D/F carry.

**Palette fit:** front card in `--accent`, back cards in `--muted`/`--muted-2`. Worth checking contrast in warm-paper specifically, where `--muted-2` (`#aaa293`) sits light-on-light against `--ground` (`#e9e3d8`).

**Production cost:** moderate — more paths and (optionally) drop-shadow layering than A/B/C at 128px+, though shadows can simply be dropped at 32px/16px since Microsoft frames them as a depth nicety, not a requirement. The banner's wordmark still needs the path-conversion/font-embedding treatment common to every direction here once it becomes a referenced README image.

#### H — Terminal bracket

**The idea in one line:** the mark is a monospace `[` `]` bracket pair with a small filled dot as a cursor/focus point inside — reusing the app's own `ui-monospace` label convention already visible in `styles.css` (e.g. the "BALANCED GRID" label styling) — and the banner frames the whole composition as literal terminal/title-bar chrome (thin 1px border, small caption dots) containing monospaced mock command lines drawn from `CONTEXT.md` vocabulary (e.g. a zone-cycle or directional-focus command), with the wordmark set as the terminal's title-bar text rather than large display type.

**Evidence:** komorebi's real public identity is CLI-first — its README has no illustrated mark, and per this repo's own prior research its whole command surface is `komorebic` ([`docs/research/automatic-tiling-managers.md`](./automatic-tiling-managers.md): "komorebi... command-line control surface"). No project examined here ships a literal terminal-chrome hero as its README banner — GlazeWM/Hyprland/yabai all use illustrated marks, komorebi/Rectangle use plain screenshots — so, like E, this is a novel combination for this space rather than a directly precedented one; flagged explicitly.

**Small-size survival:** the best of the five for the icon specifically alongside F — a bracket pair is about as close to Microsoft's "as few shapes with as few corners as possible" ideal as a distinctive mark can get (two strokes plus a dot), and stays legible down to 16px the way punctuation-style marks generally do.

**Palette fit:** bracket + dot in `--accent`, both palettes trivially. The terminal-chrome banner reuses `--panel`/`--ground` backgrounds and `--muted`/`--ink` text tones already defined in `styles.css` — zero new tokens required.

**Production cost:** the cheapest mark of the five to draw (two strokes, one dot). The banner needs literal monospace text content authored — live `<text>` works fine for an in-app prototype route, but per the font-portability finding above it needs path-conversion or an embedded font for the actual README asset. This is the one direction with a legitimate way to dodge that cost entirely: since the content is already "terminal output," the banner could instead ship as a real screenshot of an actual terminal window (reusing F's raster/`<picture>` mechanics) rather than an illustrated SVG.

### Trade-offs

**Cheapest to ship today:** H for the icon (two strokes, zero new palette tokens) and, if the banner leans on a real terminal screenshot instead of illustrated text, H sidesteps the font-portability cost every SVG-based direction otherwise carries. F's icon is equally cheap, but F's banner is blocked on the product having a screen worth showing, which `README.md`'s own "Early development" status line says it doesn't yet.

**Best 16px survival:** H and F's icons, by a clear margin — both are close to Microsoft's "fewest shapes, fewest corners" ideal. D is workable but needs a tested, possibly simplified, 16px variant. G is the weakest and most likely to need a dedicated small-size fallback. E's icon directly runs into Microsoft's stated "avoid typography in icons" guidance, independent of size.

**Best domain-vocabulary encoding:** D (**Directional focus**, **Directional swap**) and G (**Focus border**, **Session-floating window**) reach into vocabulary A/B/C don't touch at all. H encodes **Zone cycle**-style commands literally as banner text but doesn't structurally build the mark itself around any glossary term the way D and G do.

**Recommendation (a recommendation, not a decision):** H balances the constraints best — cheapest icon, safest at 16px, zero new palette tokens, and a legitimate escape hatch from the font-portability problem for its banner. If the team wants the mark itself to carry more of the domain vocabulary rather than leaning on literal command text, D is the runner-up, with the explicit caveat that its 16px tick legibility needs to be test-rendered before committing, not assumed from this document alone.
